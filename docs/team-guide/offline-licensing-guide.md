# راهنمای لایسنس آفلاین (Offline Licensing)

هدف این سند: توضیح دقیق توکنی که Keygate برمی‌گرداند و اینکه چطور در نرم‌افزار مشتری
**بدون اینترنت** اعتبارسنجی شود. همهٔ جزئیات از `internal/license/token.go` و
`internal/service/license.go` گرفته شده‌اند.

---

## ۱. چرا Ed25519 و نه HMAC؟

Keygate عمداً از **امضای نامتقارن Ed25519** استفاده می‌کند، نه HMAC.

* HMAC متقارن است: هرکس بتواند بررسی کند، می‌تواند امضا هم بسازد. اگر کلید مشترک داخل فایل
  اجرایی دسکتاپ باشد، قابل استخراج است و مهاجم می‌تواند لایسنس جعلی بسازد.
* Ed25519 کلید **خصوصی** را روی سرور نگه می‌دارد؛ کلاینت فقط کلید **عمومی** را دارد و می‌تواند
  امضا را بررسی کند، ولی نمی‌تواند بسازد.

---

## ۲. شکل توکن

توکن یک رشتهٔ متنی است:

```
base64url(payload_json) + "." + base64url(signature)
```

* `payload_json` = JSON ساختار `VerifyToken`.
* امضا روی **بایت‌های همان نیمهٔ اول (رشتهٔ base64)** محاسبه می‌شود، **نه** روی JSON خام.
  این نکته حیاتی است: وقتی خودتان بررسی می‌کنید، باید `const b64 = token.split('.')[0]` را
  بردارید و `ed25519.verify(publicKey, utf8Bytes(b64), signatureBytes)` را اجرا کنید.
* هر دو بخش با **base64url بدون padding** (`RawURLEncoding`) کدگذاری شده‌اند.
* جداکننده `.` است و آخرین نقطه جداساز شمرده می‌شود.

## ۳. فیلدهای payload

| کلید JSON | نام Go | نوع | معنا |
|---|---|---|---|
| `lid` | LicenseID | string | شناسهٔ لایسنس |
| `pid` | ProductID | string | شناسهٔ محصول (برای تطبیق با کلید عمومی/محصول) |
| `pln` | PlanID | string | شناسهٔ پلن |
| `sts` | Status | string | وضعیت لایسنس (`active`, `trialing`, `past_due`, `canceled`, …) |
| `did` | Identifier | string | شناسهٔ دستگاه/کاربری که توکن برایش صادر شده |
| `ftr` | Features | object (اختیاری) | نقشهٔ قابلیت‌ها→مقدار (منبع همان چیزی است که verify در `features` می‌دهد) |
| `iat` | IssuedAt | int64 | زمان صدور (unix second) |
| `exp` | ExpiresAt | int64 | **انقضای خودِ توکن** (بازهٔ check-in)، نه انقضای لایسنس |
| `vun` | ValidUntil | int64 (اختیاری) | زمان پایان خودِ لایسنس؛ صفر/غایب = دائمی |
| `upd` | UpdatesUntil | int64 (اختیاری) | پایان دورهٔ نگهداری؛ صفر/غایب = بدون سقف جداگانه |
| `grc` | GraceDays | int | روزهای مهلت اعمال‌شده |
| `nce` | Nonce | string | مقدار یکتا برای هر صدور (ضد replay) |
| `fpr` | Fingerprint | string (اختیاری) | `SHA256(identifier + ":" + product_id)` کوتاه‌شده به ۸ بایت (hex) |
| `ver` | Version | string | نسخهٔ قالب توکن؛ `Sign` آن را `"1"` می‌گذارد |
| `kid` | KeyID | string | شناسهٔ کلید امضا: `key_` + ۱۶ hex از `sha256(public_key)`؛ `Sign` خودش آن را پر می‌کند. کلاینت باید کلید را **با همین `kid`** از `/license/pubkey` بگیرد |

نمونهٔ payload (ساختگی):

```json
{
  "lid": "lic_01HXYZ",
  "pid": "prod_01ABCD",
  "pln": "plan_pro",
  "sts": "active",
  "did": "machine-abc",
  "ftr": { "export": true, "seats": 5 },
  "iat": 1760000000,
  "exp": 1760604800,
  "vun": 1791536000,
  "upd": 1791536000,
  "grc": 7,
  "nce": "q83vA1bZ...",
  "fpr": "9f2c1a7b3d4e5f60"
}
```

## ۴. گرفتن کلید عمومی

```
GET /api/v1/license/pubkey
```

پاسخ (بدون نیاز به اعتبارنامه) هم شکل تک‌کلیدی و هم چندکلیدی دارد:

```json
{
  "algorithm": "ed25519",
  "format": "hex",
  "kid": "key_ed98fe3cb95b2d47",
  "public_key": "<64 hex chars>",
  "keys": [
    {
      "kid": "key_ed98fe3cb95b2d47",
      "algorithm": "ed25519",
      "format": "hex",
      "public_key": "<64 hex chars>",
      "status": "active"
    }
  ]
}
```

* `public_key` یک کلید **۳۲ بایتی** است که به‌صورت hex داده می‌شود.
* هدر پاسخ `Cache-Control: public, max-age=3600` است؛ می‌توانید کش کنید.
* توکن‌های جدید فیلد `kid` دارند. **کلید را با همان `kid` انتخاب کنید** (از آرایهٔ `keys`)،
  نه صرفاً اولین کلید. `status` می‌تواند `active` یا `retired` باشد؛ برای توکن تازه فقط
  `active` معتبر است و `retired` برای توکن‌های قدیمی نگه داشته می‌شود.
* توکن‌های قدیمی بدون `kid` تنها با کلید پیش‌فرض/تک‌کلیدی بررسی می‌شوند.
* توصیه: کلید(ها) را یک‌بار دریافت و در بیلد بعدی **جاسازی (pin)** کنید تا اگر سرور در دسترس
  نبود، اعتبارسنجی آفلاین همچنان کار کند. (عملیات rotation کلید، کلاینت را وادار به
  دوباره‌گرفتن می‌کند.)

---

## ۵. الگوریتم اعتبارسنجی (مستقل از زبان)

1. توکن را روی آخرین `.` به `payloadB64` و `sigB64` تقسیم کنید.
2. `sig = base64url_decode(sigB64)` → باید ۶۴ بایت باشد.
3. `ok = ed25519.verify(pubKey, utf8Bytes(payloadB64), sig)`.
4. اگر `ok` نبود → توکن جعلی/تغییر‌یافته است، رد کنید.
5. `payload = json_parse(base64url_decode(payloadB64))`.
6. زمان فعلی `now` (unix seconds):
   * اگر `exp > 0 && now > exp` → توکن منقضی است (باید دوباره verify آنلاین شود).
   * اگر `vun > 0 && now > vun + (grc * 86400)` → لایسنس واقعاً مرده است.
   * اگر `upd > 0` → نسخه‌های منتشرشده بعد از `upd` نباید نصب شوند.
7. اختیاری: `fpr == SHA256(identifier + ":" + product_id)[0..8]` را برای تطبیق دستگاه بررسی کنید.

> **مهم:** بررسی امضا را همیشه **قبل از** اعتماد به محتوای payload انجام دهید.

---

## ۶. معنای `exp` در برابر `vun`

* `exp` = «تا چه زمانی کلاینت می‌تواند آفلاین بماند». پیش‌فرض ۷ روز؛ پلن می‌تواند با
  `token_ttl_days` آن را تغییر دهد.
* سرور `exp` را طوری **کلمپ** می‌کند که هرگز از عمر لایسنس بیشتر نشود:
  `exp = min(now + TTL, valid_until + grace)`.
  یعنی اگر لایسنس فردا تمام شود، توکن هم فردا (+ مهلت) تمام می‌شود، نه ۷ روز بعد.
* `vun` = تاریخ پایان لایسنس است و **داخل payload امضاشده** قرار دارد تا کسی نتواند در مسیر
  آن را دستکاری کند. قبلاً این مقدار فقط در envelope اطراف بود (بدون امضا) و همین یک حفره بود.

---

## ۷. بازهٔ مهلت (Grace) و `grc`

* `grc` تنها برای وضعیت‌های `active`/`trialing`/`past_due` مقدار پلن را دارد؛ برای
  `canceled`/`suspended`/`revoked`/`expired` مقدارش **صفر** است.
* دلیل: یک لایسنس لغوشده تا `valid_until` استفاده می‌شود و بعد از آن **بی‌درنگ** متوقف می‌شود؛
  نباید مهلتی به آن داد که سرور قبول ندارد. اگر `grc` صفر نمایش داده شود، کلاینت نباید مهلت
  اضافه اعمال کند.

---

## ۸. اثر انگشت دستگاه (`fpr`)

```go
func Fingerprint(identifier, productID string) string {
    h := sha256.Sum256([]byte(identifier + ":" + productID))
    return hex.EncodeToString(h[:8]) // 16 hex chars
}
```

* یک توکن که از دستگاه A لو برود، روی دستگاه B (با همان کلید لایسنس ولی `identifier` متفاوت)
  قابل استفاده نیست، چون `fpr` روی `(identifier, product_id)` بسته می‌شود.

## ۹. گردش کار پیشنهادی کلاینت

```
راه‌اندازی برنامه:
  1. اگر توکن ذخیره‌شده داریم و معتبر است (امضا + exp + vun) → حالت آفلاین مجاز.
  2. اگر توکن نداریم یا منقضی شده → تلاش برای verify آنلاین:
       POST /api/v1/license/verify {license_key, identifier}
     - موفق → توکن جدید را ذخیره کن.
     - 404 LICENSE_NOT_FOUND → لایسنس نامعتبر/غیرفعال.
     - خطای شبکه → در بازهٔ مهلت با توکن قدیمی ادامه بده، وگرنه (اگر grc=0) قفل کن.
  3. برای اولین فعال‌سازی روی دستگاه جدید:
       POST /api/v1/license/activate {license_key, identifier}
```

نکات:

* `activate` و `verify` هر دو `token` می‌دهند؛ تفاوت در این است که `activate` رکورد دستگاه را
  می‌سازد (تو سقف پلن) و `verify` فقط بررسی می‌کند.
* تکرار `activate` برای همان دستگاه، `already_activated` می‌دهد (خطا نیست).
* برای آزادکردن یک سهم روی دستگاه دیگری، `POST /license/deactivate`.
* اگر الگوریتم شناسهٔ دستگاه را عوض کردید (مثلاً از UUID به `kgid:v1`)، در اولین
  `activate` فیلد `previous_identifier` را با شناسهٔ قبلی بفرستید تا **همان رکورد** منتقل شود
  و سهم جدیدی مصرف نشود (audit: `migrated`).

### ۹.۱ مسیر جایگزین: توکن صادرشده توسط ادمین

برای محیط‌های بسته (بدون دسترسی کلاینت به سرور) ادمین می‌تواند از پنل یا API مدیریتی
توکن آماده بگیرد:

```bash
curl -X POST -b cookie.txt -H 'Content-Type: application/json' \
  -d '{"identifier":"uuid:3f2a...","label":"PC-Office"}' \
  http://localhost:9000/api/v1/admin/licenses/<license_id>/offline-token
# → {"success":true,"data":{"token":"<payload>.<sig>","status":"activated",...}}
```

* این فراخوانی **یک فعال‌سازی واقعی** انجام می‌دهد؛ پس سهم دستگاه مصرف می‌شود و رکورد در
  لیست activationها دیده می‌شود (با `scheme` و `status`).
* توکن را می‌توان از قبل داخل نصب‌کننده قرار داد؛ کلاینت فقط باید امضا را با کلید عمومی
  `GET /api/v1/license/pubkey` بررسی کند.
* `identifier` باید دقیقاً همان چیزی باشد که کلاینت در `verify` می‌فرستد (وگرنه `did` تطبیق
  نمی‌کند). شناسهٔ دارای فاصله در ابتدا/انتها رد می‌شود.

## ۱۰. چرخهٔ عمر توکن و انقضا

* توکن کوتاه‌عمر است (پیش‌فرض ۷ روز). کلاینت باید پیش از `exp` دوباره verify کند.
* یک حلقهٔ background در کلاینت که هر چند ساعت یک‌بار (مثلاً هر ۲۴ ساعت) verify می‌زند،
  استاندارد است.
* اگر لایسنس **دائمی** باشد، `vun` غایب است (یعنی صفر) و فقط `exp` ملاک check-in است.
* اگر پلن دورهٔ نگهداری دارد، `upd` می‌آید؛ آپدیتر باید آن را رعایت کند.

## ۱۱. خطاهای مربوط به مسیر آفلاین

| کد | وضعیت | توضیح | تفسیر کلاینت |
|---|---|---|---|
| `LICENSE_NOT_FOUND` | ۴۰۴ | کلید ناموجود/محصول دیگر/حالت غیرقابل‌استفاده (در verify) | لایسنس نامعتبر؛ در بازهٔ مهلت به توکن ذخیره‌شده تکیه کن |
| `FEATURE_NOT_AVAILABLE` | ۴۰۴ | محصول از فعال‌سازی پشتیبانی نمی‌کند (مثلاً `saas`) | این endpoint برای این محصول وجود ندارد |
| `LOCKED_OUT` | ۴۲۹ | قفل بروت‌فورس با `details.retry_after` | به‌مدت `retry_after` صبر کن |
| `ACTIVATION_LIMIT` | ۴۰۹ | عبور از سقف دستگاه | باید دستگاهی را deactivate کنی |
| `LICENSE_EXPIRED` / `LICENSE_CANCELED` / `LICENSE_SUSPENDED` / `LICENSE_REVOKED` | ۴۰۳ | اینها فقط در مسیر `activate` ظاهر می‌شوند؛ `verify` همه را به ۴۰۴ تبدیل می‌کند | در activate می‌توانی پیام دقیق‌تر نشان دهی |

---

## ۱۲. چه چیزی را **نباید** کرد

* امضا را روی JSON خام چک نکن (باید روی رشتهٔ base64 نیمهٔ اول باشد).
* نباید به `exp` به‌عنوان «پایان لایسنس» تکیه کنی (`vun` پایان لایسنس است).
* نباید کلید خصوصی یا `LICENSE_SIGNING_KEY` را در کلاینت بگذاری.
* نباید فقط به عدم موفقیت شبکه، لایسنس را «معتبر» فرض کنی بدون بررسی امضا و انقضا.
* نباید انتساب AGPL را حذف کنی.

## ۱۳. آزمون سریع توکن (مفهومی)

```bash
# 1) گرفتن کلید عمومی
curl -s http://localhost:9000/api/v1/license/pubkey
```

سپس در کد، برای توکنی که از `verify` گرفته‌اید همان الگوریتم بخش ۵ را اجرا کنید. اگر
امضا معتبر بود ولی `exp` گذشته بود، توکن را کنار بگذارید و دوباره verify بزنید.
